# T2.3 — Grid Outage Forecaster + Appliance Prioritizer

Tier 2 · EnergyTech · Time-Series · Actionable AI

This repo solves the Day 2 AIMS KTT challenge: forecast the next 24 hours of outage risk and expected outage duration, then turn that forecast into a business-specific load-shed plan that keeps the most important appliances running first.

## What is in the repo

- `generate_synthetic_data.py` — regenerates the challenge data if the provided files are missing.
- `forecaster.py` — 24-hour-ahead probabilistic outage forecaster.
- `prioritizer.py` — appliance planning rule that enforces **drop luxury before critical**.
- `prepare_submission.py` — trains the models, evaluates them, builds artifacts, and renders the static UI.
- `eval.ipynb` — notebook that reloads held-out predictions and recomputes metrics.
- `lite_ui.html` — static lightweight page showing today's forecast band and the salon plan.
- `digest_spec.md` — product and business adaptation artifact.
- `process_log.md` — declared tool use and build log.
- `SIGNED.md` — honor code.

## Problem framing

Small businesses lose money when outages hit unexpectedly. The solution here has two pieces:

1. **Forecasting** — estimate `P(outage)` and `E[duration | outage]` for each of the next 24 hours.
2. **Planning** — for a chosen business archetype, decide which appliances stay `ON` or go `OFF` each hour so revenue keeps flowing while honoring the rule that luxury appliances must drop before critical ones.

## Approach

### 1) Forecast model

I used a fast CPU-only baseline with lagged features available 24 hours ahead:

- hour of day, day of week, weekend flag
- `load_lag24`, `load_lag48`, `load_lag168`
- `rain_lag24`, `rain_lag48`, `rain_lag168`
- `temp_lag24`, `humidity_lag24`, `wind_lag24`
- `outage_lag24`, `duration_lag24`
- 24-hour rolling rain summary and a same-hour historical outage rate

Models:

- **Outage probability**: Logistic Regression with standardization
- **Conditional duration**: Ridge regression on `log1p(duration)` using only outage rows

Why this choice:

- retrains quickly on CPU,
- easy to explain in Live Defense,
- produces calibrated probabilities for the Brier score,
- does not depend on heavy external packages.

### 2) Evaluation

The held-out evaluation uses the **last 30 days** in a daily walk-forward loop:

- train on all data before day `D`
- predict the next 24 hours for day `D`
- collect all predictions across the held-out month

Metrics reported:

- **Brier score** for `P(outage)`
- **MAE** for `E[duration | outage]` on true outage hours
- **average lead time** on true outages for hours that crossed the planning threshold

### 3) Appliance planning

For each hour:

- compute a risk-adjusted power cap from `P(outage)` and expected duration,
- keep all appliances if the hour is low risk,
- if risk is elevated, drop appliances in this order:
  1. `luxury`
  2. `comfort`
  3. `critical`
- within the same category, break ties by **lower revenue per watt first**, then **higher startup spike**.

This keeps the planning rule easy to defend on screen while still being revenue-aware.

## Current results

From `artifacts/metrics.json`:

- **Brier score:** `0.0391`
- **Duration MAE on true outages:** `39.78 min`
- **Average lead time on true outages:** `15.33 h`
- **Planning threshold:** `0.06`

Top logistic features in the final model:

1. `dow`
2. `is_weekend`
3. `load_lag24`
4. `rain_lag48`
5. `rain_lag168`

For the salon archetype, the current plan estimates an expected weekly gain of about **80,367 RWF** relative to a naive full-on strategy during elevated-risk hours.

## Product and business adaptation

The required offline / low-bandwidth adaptation is in `digest_spec.md`.

Highlights:

- a **3-SMS morning digest** for the salon owner,
- explicit behavior when the forecast cannot refresh mid-day,
- a **6-hour staleness budget** before the plan falls back to critical-only,
- an accessibility choice for users who cannot read.

## Lite UI design

`lite_ui.html` is intentionally lightweight:

- static HTML,
- no external network dependency,
- small enough for low-bandwidth sharing,
- renders the 24h outage band and the salon appliance grid.


## Known limitations

- The outage forecaster is intentionally simple and favors clarity over maximum accuracy.
- The expected-revenue benchmark in the planner is operational rather than a physical power-flow simulation.
- The UI is static by design to satisfy the low-bandwidth requirement; it is not a live web app.
- A next iteration would add crowd outage reports or feeder-level neighbor signals.
